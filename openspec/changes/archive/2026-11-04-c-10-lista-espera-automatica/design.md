# Design

## Context

Ver `proposal.md` §Why. El estado relevante del código:

- C-06 expone `crear_turno` y `reprogramar_turno` en `backend/app/application/turnos.py`; el anti-solapamiento es una exclusion constraint de PostgreSQL (`agenda.py`, `ex_turnos_profesional` / `ex_turnos_sillon`) más validación previa en `validar_solapamiento`, compartida por backoffice y reserva pública.
- C-07 tiene la autoasignación de sillón `_elegir_sillon` en `backend/app/api/publico.py`; la disponibilidad pública vive en `GET /reservar/{slug}/disponibilidad` y la del backoffice en `GET /profesionales/{id}/disponibilidad` (`api/profesionales.py`). Ambas descuentan turnos activos y bloqueos con `calcular_disponibilidad`.
- C-09 dejó `MensajeWhatsApp` (`plantilla` ya admite `oferta_hueco`), la cola `whatsapp:send`, el worker de reintentos y un único emisor de `RegistroAuditoria(accion="hueco_liberado")` dentro de `application/webhooks.py`.
- Las cancelaciones ocurren en tres lugares: `PATCH /turnos/{id}/estado`, `POST /reservar/gestion/{token}/cancelar` y la rama «cancelar» del webhook. Solo la tercera emite hoy el evento de hueco liberado.
- R-06 y `platform/job-queues` fijan exactamente tres nombres de cola (`whatsapp:send`, `recordatorios:due`, `arca:emitir`); no se agregan colas nuevas.
- Head real de migraciones: `0008_whatsapp_recordatorios`.

## Goals / Non-Goals

**Goals:**
- Un único punto de disparo del hueco liberado, invocado por las tres cancelaciones.
- FIFO determinista y compatible, con oferta de una sola entrada por hueco.
- Retención atómica del horario ofrecido (profesional + sillón + rango) mientras la oferta está vigente.
- Oferta entregada por el canal y la plantilla que ya existen, sin costo real en v1.
- Vencimiento y rotación sin agregar colas ni depender de delays de Redis.
- Conversión transaccional con la garantía de no solapamiento de C-06 y el sillón retenido.

**Non-Goals:**
- Autogestión pública para anotarse en la lista de espera (queda para una iteración posterior; ver Open Questions).
- Crear un estado nuevo de turno (`propuesto`/`pendiente_de_aceptación`): la retención vive en la entrada de lista de espera, no en `turnos`.
- UI de backoffice o página de oferta en React (C-10 es API; el test de páginas queda para el cierre).
- Priorización por urgencia clínica, múltiples ofertas simultáneas al mismo paciente o reprogramación desde la oferta.
- Proveedor real de Meta (sigue `WHATSAPP_PROVIDER=test`, R-12).

## Decisions

### D1 — Señal del hueco liberado: servicio de aplicación, no consumo de auditoría

Se agrega `registrar_hueco_liberado(uow, turno, *, now=None)` en `app/application/lista_espera.py` y se llama desde las tres cancelaciones. El servicio escribe `RegistroAuditoria(accion="hueco_liberado")` (se mueve el registro que hoy vive en `webhooks.py`) y ejecuta `ofrecer_hueco(...)` en la misma transacción.

**Por qué no consumir el evento de auditoría:** hoy solo el webhook lo emite, así que la lista perdería las cancelaciones de recepción y del enlace público. Además `registro_auditoria` es append-only y no es un transporte: habría que inventar un poller con cursor sobre una tabla de auditoría, con entrega al menos una vez y deduplicación. La exclusion constraint de retención (D2) evitaría duplicados, pero el costo y el acoplamiento son mayores que tres llamadas explícitas a un servicio testeable.

**Trade-off:** una cancelación nueva en el futuro debe recordar llamar al servicio. Mitigación: los tests de integración cubren las tres rutas y el servicio es el único lugar donde vive la regla.

### D2 — Modelo `EntradaListaEspera` y migración `0009_lista_espera`

Tabla `entradas_lista_espera` (nombre en plural, coherente con el resto):

| Columna | Tipo / regla |
|---|---|
| `id` | UUID PK |
| `consultorio_id` | UUID FK `consultorios`, NOT NULL |
| `paciente_id` | UUID FK `pacientes`, NOT NULL |
| `prestacion_id` | UUID FK `prestaciones`, NOT NULL |
| `profesional_id` | UUID FK `profesionales`, NULL (sin preferencia) |
| `orden` | `BIGINT` `GENERATED BY DEFAULT AS IDENTITY`, NOT NULL, UNIQUE |
| `estado` | `pendiente`, `ofrecido`, `convertido`, `vencido` (CHECK), default `pendiente` |
| `oferta_inicio` | timestamptz NULL |
| `oferta_fin` | timestamptz NULL (`fin` original del turno liberado) |
| `oferta_profesional_id` | UUID FK `profesionales`, NULL |
| `oferta_sillon_id` | UUID FK `sillones`, NULL |
| `oferta_expira_en` | timestamptz NULL |
| `turno_id` | UUID FK `turnos`, NULL, único parcial (una oferta → un turno) |
| `is_active`, `created_at`, `updated_at`, `deleted_at` | `AuditMixin` (baja lógica) |

CHECKs: `(deleted_at IS NULL) = is_active`; `estado <> 'ofrecido' OR (oferta_inicio IS NOT NULL AND oferta_fin > oferta_inicio AND oferta_profesional_id IS NOT NULL AND oferta_sillon_id IS NOT NULL AND oferta_expira_en IS NOT NULL)`; `estado <> 'convertido' OR turno_id IS NOT NULL`; `estado <> 'pendiente' OR oferta_inicio IS NULL`.

Constraints de exclusión (la retención como recurso de agenda, `btree_gist` ya habilitado por C-06):

```sql
ALTER TABLE entradas_lista_espera
  ADD CONSTRAINT ex_lista_espera_profesional
  EXCLUDE USING gist (
    oferta_profesional_id WITH =,
    tstzrange(oferta_inicio, oferta_fin, '[)') WITH &&
  ) WHERE (estado = 'ofrecido' AND deleted_at IS NULL);

ALTER TABLE entradas_lista_espera
  ADD CONSTRAINT ex_lista_espera_sillon
  EXCLUDE USING gist (
    oferta_sillon_id WITH =,
    tstzrange(oferta_inicio, oferta_fin, '[)') WITH &&
  ) WHERE (estado = 'ofrecido' AND deleted_at IS NULL);
```

Como el predicado exige `estado='ofrecido'`, pasar a `convertido`, `vencido` o hacer la baja lógica saca la fila del índice y libera la retención en la misma sentencia.

Índices:
- `ix_entradas_lista_espera_cola (consultorio_id, estado, orden)`.
- `ix_entradas_lista_espera_prestacion (prestacion_id, estado, orden)`.
- `ix_entradas_lista_espera_vencimiento (estado, oferta_expira_en)` para el barrido.
- `ix_entradas_lista_espera_retencion (oferta_profesional_id, oferta_inicio)` y `(oferta_sillon_id, oferta_inicio)` para las consultas de disponibilidad/alta (los índices GiST de exclusión no sirven bien para rangos abiertos con `now`).
- `uq_entradas_lista_espera_pendiente` único parcial sobre `(paciente_id, prestacion_id, coalesce(profesional_id, '00000000-0000-0000-0000-000000000000'::uuid))` con `estado='pendiente' AND deleted_at IS NULL` (el `coalesce` cubre el caso sin profesional, que en un índice único normal quedaría duplicable).

La misma migración ajusta `mensajes_whatsapp`:
- `turno_id` pasa a `NULL`.
- nueva columna `lista_espera_id UUID NULL` FK a `entradas_lista_espera`.
- CHECK `respuesta_valida` pasa a incluir `aceptado` y `rechazado`.
- CHECK de coherencia: `turno_id IS NOT NULL OR lista_espera_id IS NOT NULL`.

**Por qué no una tabla `ofertas_hueco` separada:** la retención es un estado transitorio de la entrada (una a la vez) y su historial útil ya queda en `mensajes_whatsapp` y auditoría. Una tabla extra obliga a un join para saber si una entrada está ofrecida, duplica el ciclo de vida (`ofrecido`/`vencido` en dos tablas) y no aporta atomicidad extra: la exclusion constraint sobre la entrada ya impide dos retenciones solapadas.

### D3 — FIFO: `orden` por identidad, no `created_at`

`orden` se genera con identidad de PostgreSQL (monótona y libre de carreras). El FIFO se define como `ORDER BY orden ASC, created_at ASC` dentro del filtro de compatibilidad. Un contador "por consultorio" (`max+1`) obligaría a un lock por alta y no aporta: en un orden global, el subconjunto de cada consultorio conserva el orden relativo. `created_at` solo se usa como desempate.

Compatibilidad:
1. `estado = 'pendiente'`, `deleted_at IS NULL`, mismo `consultorio_id` y misma `prestacion_id`.
2. `profesional_id IS NULL OR profesional_id = :profesional_del_hueco`.
3. No se compara especialidad del profesional: el hueco ya es un turno válido de esa prestación con ese profesional.

### D4 — Claim atómico: `FOR UPDATE SKIP LOCKED` para la cola y `UPDATE ... RETURNING` para los estados

Oferta (una sola entrada por hueco):

```sql
SELECT id FROM entradas_lista_espera
WHERE consultorio_id = :c AND prestacion_id = :p AND estado = 'pendiente'
  AND deleted_at IS NULL
  AND (profesional_id IS NULL OR profesional_id = :prof)
ORDER BY orden, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

La fila queda bloqueada hasta el commit y se actualiza a `ofrecido` escribiendo `oferta_profesional_id`, `oferta_sillon_id`, `oferta_inicio`, `oferta_fin` y `oferta_expira_en`. Dos huecos simultáneos no pueden reclamar la misma entrada; dos procesos por el mismo hueco no pueden reclamar dos entradas porque el primero bloquea la de menor orden y el segundo, si llega antes del commit, obtiene la siguiente (`SKIP LOCKED`) — se evita el doble ofrecimiento de un mismo hueco porque la cancelación que lo origina es una sola transición de estado del turno.

La retención se protege además con las exclusion constraints de D2: si dos cancelaciones liberan rangos que se solapan (por ejemplo, un turno normal y un sobreturno), la segunda actualización viola `ex_lista_espera_profesional` o `ex_lista_espera_sillon` con SQLSTATE `23P01`. El servicio traduce ese error a «hueco ya retenido», no emite oferta para ese rango y deja la otra retención intacta.

Antes de retener, `ofrecer_hueco` marca como `vencido` toda retención solapada con `oferta_expira_en <= now` (purga perezosa dentro de la misma transacción). Sin esa purga, una fila vencida que el worker todavía no barrió seguiría en el índice de exclusión y haría fallar con `23P01` una retención nueva del mismo rango.

Vencimiento y aceptación usan `UPDATE ... WHERE id = :id AND estado = :esperado [AND oferta_expira_en <= now] RETURNING id`: solo un worker gana el vencimiento, y la aceptación reclama la fila con `SELECT ... FOR UPDATE` antes de crear el turno (ver D6).

### D5 — Vencimiento en PostgreSQL + tick del scheduler; sin cola nueva

Se guarda `oferta_expira_en` (TTL `LISTA_ESPERA_OFERTA_TTL_MINUTOS`, default 30). `procesar_ofertas_vencidas(uow, redis, now)` se llama desde el tick existente `run_once_recordatorios` y desde el loop `recordatorios`. Para cada vencida: claim atómico con `UPDATE ... WHERE estado='ofrecido' AND oferta_expira_en <= now RETURNING *`, `flush` para que la fila salga del índice de exclusión y libere la retención, auditoría `oferta_hueco_vencida`, revalidación de que el hueco sigue libre y rotación a la siguiente entrada (que retiene de nuevo).

**Vencimiento perezoso:** todas las lecturas y validaciones de retención usan `estado = 'ofrecido' AND oferta_expira_en > now`. Si el worker está detenido, una oferta vencida deja de ocultar el slot y de bloquear altas en el instante del vencimiento, aunque la fila siga `ofrecido` y la rotación espere al scheduler. El barrido sigue siendo necesario para rotar y para limpiar el estado.

**Por qué no un job con delay en Redis:** R-06 prohíbe usar Redis como fuente de verdad y la lista `whatsapp:send` no soporta delay; C-09 ya resolvió lo mismo con `programado_para` + barrido. **Por qué no una cola `lista_espera:due`:** `platform/job-queues` fija tres nombres y agregar uno exige modificar esa capability; el barrido por `(estado, oferta_expira_en)` es barato con el índice y no necesita un cuarto nombre.

El TTL se configura por variable de entorno (global en v1), no por consultorio: alcanza para US-003/CA-2 y evita tocar la tabla `consultorios`. Queda como extensión natural si se pide por consultorio.

### D6 — Aceptación transaccional: token, savepoint y resultado explícito

Orden de la aceptación por enlace:

1. `consume_single_use_token(session, token, "oferta_hueco")` → 410 si usado/vencido/otro propósito.
2. Cargar la entrada con `SELECT ... FOR UPDATE`; si no está `ofrecido`, ya venció o `oferta_expira_en <= now` → 410 (el token ya quedó consumido en esta transacción).
3. `async with uow.session.begin_nested(): turno = await crear_turno(..., prestacion_id=entrada.prestacion_id, profesional_id=entrada.oferta_profesional_id, sillon_id=entrada.oferta_sillon_id, inicio=entrada.oferta_inicio, retencion_excluida=entrada.id)` — un `409` revierte solo el savepoint, no el consumo del token ni el estado de la entrada. `retencion_excluida` evita que la propia retención que se está convirtiendo bloquee el alta; cualquier otra retención vigente sigue bloqueando.
4. Camino feliz: entrada `convertido` + `turno_id`, `flush` (la fila sale del índice de exclusión y la retención queda liberada), el UoW commitea todo.
5. Camino 409: entrada `vencido` (libera la retención), auditoría `oferta_hueco_perdida`, rotación al siguiente, y el caso de uso **devuelve un resultado** (`TurnoCreado | HuecoOcupado`) en lugar de lanzar. El router traduce a 200/409. Así el consumo del token y el `vencido` se commitean aunque la respuesta sea de error.

**Por qué no lanzar `HTTPException`:** el `UoW` hace rollback ante excepción y el token volvería a quedar usable, permitiendo reintentos infinitos sobre un hueco perdido. También se descarta consumir el token en una transacción aparte (`uow.commit()`): complica el test y deja ventanas de inconsistencia.

Dos aceptaciones concurrentes (enlace y WhatsApp) se serializan con el `FOR UPDATE` de la entrada: la segunda ve `convertido` y responde 409/410.

### D7 — Retención del hueco ofrecido: columnas de la entrada + exclusion constraints parciales

La oferta **sí retiene** el horario hasta que se acepta, se rechaza o vence. La retención se guarda en la propia entrada (`oferta_profesional_id`, `oferta_sillon_id`, `oferta_inicio`, `oferta_fin`, `oferta_expira_en`) y solo existe mientras `estado='ofrecido' AND deleted_at IS NULL`. No se crea un turno ni un bloqueo: es un recurso de agenda más, con su propio ciclo de vida.

**Atomicidad:** las dos exclusion constraints de D2 (profesional y sillón, sobre `tstzrange(oferta_inicio, oferta_fin)`) hacen que dos retenciones solapadas sean imposibles a nivel PostgreSQL, incluso por SQL directo. La selección FIFO con `FOR UPDATE SKIP LOCKED` elige una sola entrada; si dos cancelaciones compiten por el mismo rango, la segunda recibe `23P01` y se traduce a «hueco ya retenido», sin segunda oferta ni segunda retención. El `estado='ofrecido'` en el predicado hace que convertir, rechazar o vencer libere la retención con la misma sentencia que cambia el estado, sin borrar filas ni un job de limpieza.

**Lectura de la retención:** `retenciones_vigentes(profesional_id, sillon_id, desde, hasta, now)` filtra `estado='ofrecido' AND oferta_expira_en > now AND deleted_at IS NULL`. Se usa en tres lugares:
1. `GET /reservar/{slug}/disponibilidad` y `GET /profesionales/{id}/disponibilidad`: las retenciones se suman a los rangos ocupados que ya recibe `calcular_disponibilidad`, igual que turnos y bloqueos.
2. `validar_solapamiento` en `application/turnos.py`: antes del retorno temprano por sobreturno, consulta retenciones y lanza 409. Como `crear_turno` y `reprogramar_turno` son compartidos, esto cubre backoffice, reserva pública y reprogramación sin duplicar la regla.
3. La aceptación: pasa `retencion_excluida=entrada.id` para que su propia retención no bloquee la conversión (ver D6).

**Trade-offs frente a alternativas:**
- *Tabla `ofertas_hueco` separada* → más joins y dos ciclos de vida sincronizados; la entrada ya es el lugar natural de la oferta.
- *Fila en `bloqueos`* → `bloqueo` es XOR profesional/sillón y no participa del anti-solapamiento de turnos; habría que crear/borrar filas y el bloqueo no distinguiría una oferta de una licencia.
- *Turno en estado `propuesto`* → cambia la máquina de estados, la agenda, los reportes y las reglas de C-06 para todos, desproporcionado para governance MEDIO.

**Riesgo residual:** la retención y los turnos viven en tablas distintas, así que PostgreSQL no puede impedir por constraint que un turno insertado en una transacción concurrente se solape con una retención recién creada. En la práctica la cancelación mantiene el turno original visible como activo hasta el commit, lo que bloquea al alta concurrente; el borde posible (cancelación de un sobreturno, que no bloquea por diseño) se resuelve en la aceptación: `crear_turno` detecta el turno ganador, responde 409, libera la retención y rota. No queda un horario doblemente reservado.

### D8 — Token de propósito `oferta_hueco` (no reutilizar `gestion_turno`)

Se emite `create_single_use_token(tipo="oferta_hueco", entidad_tipo="entrada_lista_espera", entidad_id=..., expires_minutes=ttl)`. TTL del token = TTL de la oferta.

**Por qué no `gestion_turno`:** ese token resuelve a un `turno_id` y `/reservar/gestion/{token}` exige un turno existente; una oferta todavía no tiene turno. Reutilizarlo obligaría a crear un turno ficticio o a ramificar la ruta de gestión por «no hay turno», ensuciando el contrato de C-07. Un propósito propio deja los dos flujos separados y auditables, y `verify_single_use_token(expected_tipo=...)` ya rechaza el cruce con 410.

Rutas públicas: `GET /reservar/oferta/{token}`, `POST /reservar/oferta/{token}/aceptar`, `POST /reservar/oferta/{token}/rechazar`. Se montan en `app/api/ofertas.py` con prefijo `/reservar/oferta`, sin JWT, igual que C-07.

### D9 — Entrega de la oferta reutilizando `MensajeWhatsApp` y `whatsapp:send`

`ofrecer_hueco` crea `MensajeWhatsApp(plantilla="oferta_hueco", lista_espera_id=entrada.id, turno_id=None, payload={telefono, variables})`, con `variables` armadas por `plantillas.variables_oferta_hueco(...)` (paciente, fecha/hora `UTC-3`, matrícula y `oferta_url`). Luego `try_enqueue(WHATSAPP_SEND, str(mensaje.id))`. Si Redis falla, `proximo_intento = now` para que `procesar_reintentos` del worker `whatsapp` lo levante; la cancelación nunca se revierte.

El webhook, antes de resolver `turno_id`, ramifica por `mensaje.plantilla == "oferta_hueco"` hacia `procesar_respuesta_oferta(...)` con las acciones `aceptar`/`rechazar`; `confirmar`/`reprogramar` sobre una oferta se derivan. La idempotencia sigue siendo la de C-09 (`proveedor_mensaje_id` + `respuesta != 'ninguna'`).

### D10 — Sillón retenido, sin tocar la autoasignación de C-07

En C-10 el sillón no se elige: la oferta retiene el mismo sillón del turno liberado y la aceptación crea el turno en ese sillón. `crear_turno` sigue validando que el sillón esté activo y habilitado; si fue dado de baja entre la oferta y la aceptación, responde 404/409, la entrada pasa a `vencido` y se rota. Por eso **no** se extrae `_elegir_sillon` de `api/publico.py`: C-07 conserva su autoasignación para reservas nuevas y C-10 usa el recurso retenido, que es justamente lo que garantiza que el paciente de la lista reciba «su» hueco.

El único cambio compartido es el parámetro opcional `retencion_excluida` de `crear_turno`/`validar_solapamiento`, usado solo por la aceptación para ignorar la retención que está convirtiendo.

### D11 — RBAC y aislamiento

| Ruta | Administrador | Odontólogo | Recepcionista | Asistente | Auditor |
|---|---|---|---|---|---|
| `POST /lista-espera`, `DELETE /lista-espera/{id}` | ✅ | ❌ 403 | ✅ | ❌ 403 | ❌ 403 |
| `GET /lista-espera`, `GET /lista-espera/{id}` | ✅ | ✅ (propios) | ✅ | ✅ | ✅ |
| `/reservar/oferta/{token}` | público con token (RN-NO-03) | — | — | — | — |

Se reutiliza `require_role` y `get_consultorio_demo_id`. El odontólogo ve solo las entradas que fijan su propio `profesional_id`; las entradas sin profesional no son «suyas» y no se le muestran. Asistente y auditor leen todo el consultorio.

El alta de una entrada por el paciente desde la reserva pública queda **fuera de alcance**: C-07 no tiene identidad verificada ni throttling para escrituras públicas y US-003 no lo exige en v1; recepción carga las entradas.

### D12 — Endpoints y contratos

- `POST /lista-espera` → 201 `EntradaListaEsperaResponse`; body `{paciente_id, prestacion_id, profesional_id?}`.
- `GET /lista-espera?estado&prestacion_id&profesional_id` → lista ordenada por `orden`; `GET /lista-espera/{id}` → detalle con oferta y `turno_id`.
- `DELETE /lista-espera/{id}` → 200 (baja lógica de una `pendiente`).
- `GET /reservar/oferta/{token}` → `{prestacion, profesional, inicio, vence_en}` sin datos sensibles.
- `POST .../aceptar` → 200 `{turno_id, inicio, fin, estado}` con el turno en los recursos retenidos; 409 si la retención venció y el horario se ocupó; 410 token inválido.
- `POST .../rechazar` → 200 `{estado: "vencido"}` y la retención liberada; 410 token inválido.
- `GET /reservar/{slug}/disponibilidad` y `GET /profesionales/{id}/disponibilidad` omiten retenciones vigentes; `POST /turnos`, `PATCH /turnos/{id}/reprogramar` y `POST /reservar/{slug}/turnos` responden 409 cuando el intervalo se solapa con una.

Todos los esquemas Pydantic v2 con `extra="forbid"` (R-01/R-02) y `reject_unexpected_query_except` en los GET con filtros.

### D13 — Configuración y operación

Nueva variable `LISTA_ESPERA_OFERTA_TTL_MINUTOS` (default 30) en `Settings` y `.env.example`. El worker `recordatorios` pasa a ejecutar `procesar_ofertas_vencidas` después de `procesar_vencidos`; no se agregan servicios a Compose ni colas nuevas. Sin worker, la rotación no ocurre, pero la retención deja de bloquear en cuanto `oferta_expira_en` pasa (D5) y el horario vuelve a estar disponible; el estado `ofrecido` se limpia cuando el scheduler vuelve a correr.

## Risks / Trade-offs

- **Retención oculta disponibilidad** → mientras la oferta está vigente el slot no se puede reservar; es el comportamiento buscado. Si el paciente nunca responde, el TTL corto (30 min) y la rotación lo liberan; el riesgo de negocio es que el paciente de la lista no conteste y el hueco quede sin usar ese intervalo.
- **Retención vs. alta concurrente** → la retención se escribe en la transacción de la cancelación y el alta valida retenciones antes de insertar; el turno original sigue visible como activo hasta el commit, lo que cierra la carrera normal. El borde con sobreturnos cancelados se resuelve en la aceptación con 409 + rotación, sin doble reserva.
- **Worker de scheduler detenido** → las entradas no rotan solas, pero las lecturas y el alta ignoran retenciones con `oferta_expira_en <= now`, así que el slot vuelve a estar disponible al vencer; la rotación espera al worker. Mismo requisito operativo que C-09.
- **Mensaje de oferta sin turno** → `turno_id` nullable y `lista_espera_id` obligan a revisar cualquier consulta que asuma turno en `mensajes_whatsapp`; el webhook ramifica por plantilla antes de resolver el turno.
- **Doble retención por concurrencia** → exclusion constraints sobre `estado='ofrecido'` + `FOR UPDATE SKIP LOCKED`; el segundo intento recibe `23P01` y no emite oferta.
- **Consumo de token en un 409** → se acepta deliberadamente: un enlace no debe reintentarse indefinidamente sobre un hueco perdido; el paciente recibe el resultado y recepción puede reubicarlo con el siguiente hueco.
- **Datos personales en el payload** → el mensaje guarda teléfono y variables como C-09; no se agrega DNI ni datos clínicos.

## Migration Plan

1. `alembic revision` con `down_revision = "0008_whatsapp_recordatorios"` y `revision = "0009_lista_espera"`.
2. `upgrade`: crear `entradas_lista_espera` con CHECKs, índices y las dos exclusion constraints de retención (requiere `btree_gist`, ya instalado por C-06); alterar `mensajes_whatsapp` (`turno_id` nullable, `lista_espera_id`, CHECKs de respuesta y coherencia).
3. `downgrade`: eliminar las exclusion constraints y los índices, revertir el CHECK de respuesta, borrar `lista_espera_id`, restaurar `turno_id NOT NULL` (falla si existen mensajes de oferta; el downgrade debe borrar primero los mensajes `oferta_hueco`) y borrar la tabla.
4. Verificar `alembic upgrade head` ⇄ `alembic downgrade -1` en la base demo y que `test_migrations_env.py` reporte `0009_lista_espera`.

## Open Questions

- ¿La clínica querrá que el paciente se anote solo en la lista desde el enlace público? Requiere identidad verificada, throttling y un formulario nuevo; no cambia el modelo ni las specs de C-10, se puede agregar después.
- ¿El TTL de la oferta debe ser por consultorio (como `plazo_cancelacion_horas`) en lugar de global? Es un cambio de columna + settings, sin impacto en el ciclo de oferta.
- ¿Conviene una pantalla de lista de espera en el backoffice? C-10 deja la API lista; la UI puede ir en la página final de validación o en un change de UI posterior.
